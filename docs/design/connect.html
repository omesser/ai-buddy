Fourth empty state: needs login

When the attached Harness answers session/new with ACP -32000 (auth required), the Chat surface names the Harness and shows the login command rather than sitting silent. This is the third state ADR-0010 forbade answering — ai-buddy never collects a credential, and the command is always for the user's own terminal.

The buttons are the same three from the connect flow below, offered here once the user has picked a Harness in Settings but before that Harness has been signed in. Clicking one runs the login command; the Shell polls for auth every 60 seconds (configurable), so a mid-session login is picked up without a restart.

Connect buttons

Three named Harnesses ship: Claude Code (via Zed's adapter), Hermes, and opencode. Each gets a button with its mark. Marks are trademarks; where vendor guidelines make that awkward, a wordmark in our own type is the safe default. All three here use wordmarks — simple, legible, and safe.

Clicking a button runs the Harness's login command and polls for auth. The buttons appear in the fourth empty state (above), and in Settings once a Harness is picked but not yet signed in. They never collect a secret — they start the Harness's own login, which writes to the Harness's own credential store.

Settings home

Once Harness is the Completer source, Settings shows which Harness is attached, whether it is connected, and the same connect action. The row uses the shared FormRow pattern so AppKit, GTK, and Win32 render it consistently. The status dot is green when signed in, gray otherwise.

Out of scope

Holding credentials (#371), auto-approve flags (ADR-0017), and which Harnesses exist (#457, #458) are all out of scope. A connect button starts the Harness's own login; it never collects, stores, or proxies a secret.
